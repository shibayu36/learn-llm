# llms-from-scratch

## 学習者

- ベテランのソフトウェアエンジニア。ただしPyTorchの使い方も、リスト内包表記などPython独特の記法も分かっていない。機械学習を勉強したことは一度もない
- 説明やコードでは、PyTorchのAPIやPython独特の記法を既知として扱わない。素直なループで書き、初出のAPIは何をするものか一言添える

## 目的

GPT-2を実装しながらLLMの仕組みを理解し、AIエージェントのプロダクト開発でLLMの基礎知識を踏まえた応用ができるようになる。

そのために、書籍『つくりながら学ぶ！LLM自作入門』の流れを参考にしつつ、理解しやすいように独自の計画で実装していく。計画は `plan.md`、進捗は `progress.md`。作業前にこの2つを読む。

## 最終的に答えられるようになりたい問い

実装した仕組みと結び付けて、次の問いに自分の言葉で答えられる状態を目指す。各Stageの説明では、関係する問いがあれば「この部品はこの問いにこう関わる」と触れる。

- コンテキストが長いほど精度が下がったり、最初の方を忘れたりするのは何故か
- プロンプトチューニングで、最初に指示を出して最後にも指示を出すサンドイッチ構造が効くのは何故か
- プロンプトキャッシュは何をキャッシュしているのか
- なぜ自信満々で間違えるのか
- fine-tuningでは何が変わっているのか
- structured outputは何故作れるのか
- LLMの得意不得意は仕組みから理解できるか
- FableやOpusといったモデル差は何から生まれるのか
- なぜシステムメッセージの方が重視されるのか
- thinkingとは何か。なぜthinkingだとtemperatureが調整できなくなったりするのか
- 蒸留とは何か
- なぜeffortを変えるとキャッシュが壊れるのか
- なぜキャッシュに有効期限があるのか

## 書籍との一致の範囲

書籍のコードや構成と完璧にそろえる必要はない。変えてはいけないのは「変えるとGPTを学ぶときに誤解する部分」だけ。

- 変えてはいけない: Attention・Causal mask・層正規化・ショートカット接続・FFN・埋め込み・出力ヘッドの計算と順序、損失の定義、生成の仕組み。変えるなら `plan.md` の「本から変える決定事項」に理由を書く
- 変えてよい: ループの単位、引数の整理、評価の手順、保存形式、変数名、print文、コメントの粒度、確認コードの構成
- 設計提案で「本どおりにするか」を毎回選択肢に出さない。学習に効く案を選び、本との差は一言添える

## 用語

コメント・説明で使う用語は書籍『つくりながら学ぶ！LLM自作入門』（Raschka "Build a Large Language Model (From Scratch)" 日本語訳）の訳語に揃える。例: Attentionスコア、Attentionの重み、コンテキストベクトル、ショートカット接続、層正規化、トークン埋め込み・位置埋め込み。独自の言い回しは使わない。

書籍PDFはリポジトリ直下 `つくりながら学ぶ！LLM自作入門.pdf`、テキスト抽出済みはリポジトリ直下 `tmp/book.txt`（`===== PAGE n =====` 区切り、PDFの通しページ。印刷ページ番号とは17ずれる: 第3章はPDF 71〜114=印刷p.53〜96、第4章はPDF 115〜152=p.97〜134）。用語を書く前に `tmp/book.txt` をgrepして書籍の表記を確認する。再抽出は `uv run --with pymupdf python` で `fitz` を使う（pypdfは本文が文字化けする）。

## コードとコメントの方針

コードは上から順に読んで理解できるように書く。

- 内包表記はforループに書き下す。型ヒントは残す
- コードに唐突に出てくる定数や特殊値（例: `EOS_TOKEN = "<|endoftext|>"`）は、本文で説明するだけでなくコード内にもコメントを入れる
- コメントは「機械学習を知らない人がLLMの仕組みを理解するのに効くもの」だけにする。判断に迷ったら「LLMの理解に効くか」で決める
  - 残す: 学習データの設計意図、語彙・tokenの意味、shapeが表すもの、x/yを1文字ずらす理由、Embeddingの表としての意味、forwardが他の位置を見ていないこと、loss/backward/stepの役割、softmax・temperature・samplingの意味、出力が次の入力になること
  - 削る: Python記法の説明（lambda、`_`、スライス、dtype、tolist）、おまじない（set_num_threads、manual_seed、super().__init__）、命名の由来
  - 削る: device・MPS・GPUなど実行環境の理解向けコメント。実行環境は「一般的なWhy / Why not」を `Config.device` に1行書くだけでよい
  - 削る: 「（deviceは使わない）」「本は〜だがここでは〜」のような本との差分や省略の注記。差分の理由は `plan.md` の「本から変える決定事項」か commit メッセージに書く。「本の calc_loss_batch に相当」のように本との対応を示す一言は残してよい

## 解説文の書き方

LLMの仕組みを説明する文章（教材本文、解説HTML、結果記録の考察）は、学習者が「読者はこの段落で何が分かるようになるか」を追える順で書く。

- 「何のために必要か・何ができるようになりたいか」を先に書き、次に「今の部品では何が足りないか」、最後に仕組みへ進む。「問題があるからこれを使う」という消去法だけで終わらせない
- 「問題→解決→仕組み」のような固定見出しテンプレートは使わない。見出しは実装・実験・まとめのような目印か、見出し自体が主張になる内容固有のものだけ
- 各処理は「一言で何をする仕組みか」（抽象化）と、小さなtoken列や2×2程度の数値例を1ステップずつ追う説明（具体化）で理解させる。shape表や式の羅列、「最後の2軸を交換」のようなPyTorch都合の操作を先頭に置かない。式は具体例の後に「式で書くと」として添える。shapeの対応は実装のコードコメントで足りる
- 数式の厳密さより「そのベクトル計算が何を意味するか」を書く。Q・K・Vを「参照する側」「参照される側」とラベル付けするだけでは説明にならない。具体的なtoken列で、内積や重み付き和の結果が何を意味するかを語る
- 具体例のtoken列は「猫 犬 猫」のような作り物でなく、「日本の通貨は円です。」のように実際にありうる日本語にし、IDは実際のTokenizerで付く番号を使う
- 比喩（レンズ・図書館・探し物の札など）は使わない。役割は機能で言う（「x_i を i が探す条件に変換する行列」など）
- 各記号・各数値の意味を実例の数値付きで表にする
- 解説HTMLは解説文が主役で、図・デモは補助。各図に「なぜ・何が分かるか」と読み方のキャプションを必ず付ける。デモで操作させるものは実際のパラメータ（W_q の数値など）そのものにし、回転・伸縮のような言い換えパラメータにしない
- 結果記録（`evaluation-results.md`、`visualization-results.md`）の構成規則は `progress.md` の「作業の決め事」に従う
