## 1. 入力の解釈

入力は `[レビュー対象] [担当名]`。省略時の対象は `diff`。担当名は `concept-correctness-reviewer`、`learnability-reviewer`、`core-message-reviewer` のいずれか。担当名だけが渡された場合は対象を省略した単独指定とする。未知の担当名は3つを案内して終了する。

このSkillはClaude Code専用。担当はファイルで定義したagentではなく、`general-purpose` のsubagentを `model: opus` で起動し、担当Skillをプロンプトで読ませる。

## 2. 対象の確定

| 入力 | 対象 |
|---|---|
| 省略 / `diff` | `gitro diff` のunstaged changes＋`gitro ls-files --others --exclude-standard` のuntracked filesの内容。stagedは含めない |
| `staged` | `gitro diff --cached` のみ |
| `branch` / `ブランチ` | `gitro diff origin/main...HEAD` |
| ファイル名（複数可） | そのファイルの全文 |
| `Stage N` | `plan.md` の該当Stage節に書かれたファイルの全文と、`progress.md` の該当Stage節が指す結果ファイル |
| その他 | 指定内容を保持して渡す |

リポジトリ直下の `tmp/learn-review/<YYYYMMDD-HHMMSS>/` を一時ディレクトリとして作り、次を保存する。

- `target.md`: 対象の種別、対象ファイルの一覧（絶対パス）、差分がある場合はそのファイル名、要件（ユーザーの依頼文と、Stage指定なら `plan.md` の該当節の到達目標）、リポジトリ直下と `llms-from-scratch/` の絶対パス。作業ツリーに対象外の未コミット変更があれば、そのファイルと範囲を書き、対象に含めないと明記する
- `diff.patch`: 差分が対象のときの差分。untrackedの内容も含める
- `worktree-before.patch`: `gitro diff HEAD` の結果と、untracked filesの一覧と内容。修正分の特定に使う

差分の内容を手で転記せず、コマンド出力をそのまま保存する。取得に失敗したら未完了として終了する。レビュー用の一時ディレクトリは対象に含めない。

## 3. フェーズ1: 3担当の並列レビュー

`concept-correctness-reviewer`、`learnability-reviewer`、`core-message-reviewer` を、1つのメッセージで3つの `Agent` 呼び出しとして同時に起動する。担当名指定のときはその1担当だけを起動する。

各subagentへのプロンプトには次を含める。

- 最初に `<リポジトリ直下>/.claude/skills/<担当名>/SKILL.md` をReadし、そのSkillに従ってレビューすること。読めなければ未完了として報告すること
- `target.md` の絶対パス。対象はそこに書かれた範囲を維持すること
- レビューのみ。コード修正・ファイルの作成・Gitの状態変更・外部投稿・他agentの起動は禁止
- 最終報告としてレポート全文を返すこと

全担当の終了を待つ。レポートは会話中のテキストとして受け取り、ファイルには保存しない。起動失敗・実行エラー・途中終了・Skill未読は未完了とする。1担当でも未完了なら修正へ進まず、完了／未完了と原因を報告して終了する。指摘なしと未完了を区別する。

## 4. フェーズ1の修正

全担当が成功した後、親が全レポートの指摘を一覧化し、1件ずつ妥当性を評価する。担当の指摘を鵜呑みにせず、技術的に正しいか、`llms-from-scratch/CLAUDE.md` の各方針と合うか、対象のコードや文章を読んで自分で確かめる。対応しない指摘には理由を書く。

担当の指摘は加筆を求めるものに偏る。加筆を求める指摘は、まず既存の文を短く書き換えて満たせないか考え、それで足りるならそちらにする。根拠・数値・観察はコメントでなく `plan.md`・`progress.md` に書く。

妥当と判断した指摘だけを逐次修正する。修正はsubagentへ委譲しない。修正ごとに `llms-from-scratch/` で `uv run` による動作確認を行う。学習を伴う確認は小さな設定に限る。修正でレビュー対応の経緯や指摘への言及をコードコメントに書かない。

修正後、`gitro diff HEAD` とuntrackedの内容を `worktree-after.patch` に保存し、`worktree-before.patch` と比べて今回の修正分を特定する。元からある対象外の未コミット変更を修正分に混ぜない。レビュー中に対象外の変更が入っていたら、同じ対象をレビューできていない旨を報告して停止する。

修正した内容と、対応しなかった指摘とその理由を `fixes.md` に書く。修正がなくても「修正なし」と書く。修正でコメント・段落が元より長くなった箇所は、`fixes.md` に「長くなった箇所」として列挙する。

## 5. フェーズ2: 修正後の伝わり方の再レビュー

正しさや学びやすさの指摘に沿って直すと、説明のコアがぼやけたり文が崩れたりすることがある。それを見るための再レビューなので、フェーズ1の修正がなければ実行せず終了する。修正があった場合のみ、`core-message-reviewer` を1つ起動し、プロンプトにフェーズ1と同じ項目に加えて次を含める。

- `fixes.md` の絶対パス。対象は `target.md` の範囲に今回の修正分を足したもので、**作業ツリーの現在の内容**を読むこと
- 解消済みの問題を古い差分から再指摘しないこと
- `fixes.md` の「長くなった箇所」と、`worktree-before.patch`・`worktree-after.patch` の比較で長くなったコメント・段落を必ず見て、増えた分がコアを際立たせるか判定すること。効かなければ削る案を「必須」で出すこと

成功時は親が妥当な指摘だけを逐次修正し、必要な動作確認をする。失敗時は伝わり方レビュー未完了と報告する。ここから再レビューへ戻らない。

## 6. 報告

最後に次を報告する。

- 各担当の完了状況（完了／未完了と原因）
- 対応した指摘と、対応しなかった指摘。指摘ごとに「担当名 #番号: 要点」の見出し、指摘内容、修正内容または対応しない理由を書く。複数の担当が同じ指摘をしていれば「concept #1 / learnability #3」のように併記する
- 動作確認の結果
- 一時ディレクトリのパス

commitはしない。
